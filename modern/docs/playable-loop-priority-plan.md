## 防止陷入細節的開發規則

1. **每輪優先完成可用介面驗收的功能切片：** 先說明這一步使「玩家在本機瀏覽器能按出什麼結果」多了哪一段，再選原版來源證據與必要測試。下一階段預設從上表**最前面尚未完成**的功能接續；不要因尚有無數未驗證函式就一直轉去新增孤立測試。
2. **只查會阻擋目前功能的細節：** 原版函式、數值、回呼、隨機性、時間邊界等，一旦會影響目前路徑的資產、計算順序、資安或存檔安全，必須原版 Perl 對照；不影響此流程的冷門商品、歷史異常與未用分支先列入待查清單，**不擴大本輪實作**。
3. **不以測試數當進度 KPI：** 新增斷言只是品質證據。每輪回報「現在能做什麼／還不能做什麼／接下來打通哪個操作」，再附上對應 CI，避免把 807/1138 當作整體完成比例。
4. **避免測試用限制固化成遊戲限制：** B-38 的人工 #10、B-39 的人工 #70、固定單店／固定1728或8640秒／明示樣本亂數，只是隔離測試；正式模組要把合法商品取得、時間／隨機性與世界狀態一般化。原版真實合法但在現有 JSON-safe 整數模型無法表達的小數，應處理資料表示／原版累積與取整語義，**不得改遊戲規則來湊測試**。
5. **持續保護來源和回歸：** 修改只在既有工作分支／Draft PR，跑同 SHA Push 與 PR CI，保留原版異常紀錄，來源不符時先拒絕功能，不暗中修原版。除非真有必要，不另外延伸原版片段專題。
6. **工作紀錄以此計畫為優先序：** [正式進度](migration-progress-and-next-milestones.md)記實際完成項目；[交接文件](next-window-handoff.md)指向本計畫並從當前第一個未完成步驟續做。後續討論若未明示要求改方向，不得自動將「再研究細節」排在真正進貨／可玩閉環之前。
